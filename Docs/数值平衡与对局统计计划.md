# 数值平衡与对局统计计划

目标：用 **AI 批量对局数据** 观察角色强弱与死亡结构，指导改 `game_rules.yaml` / 卡牌数值，再复跑验证。  
原则：指标是「当前 AI 策略下的平衡方向灯」，不是真人平衡的最终结论。

---

## 1. 仿真真源（已切换）

**对局真源 = Unity `Game/Assets/Scripts`（LogicSim）**，由 `Tools/sim` 编排拉起。  
独立 Python 规则引擎已移除；平衡与 QA 造数仅走 Unity。

| 能力 | 说明 |
|--|--|
| 四角色全 AI | Game `SimpleHeuristicAi`，进程内连跑 |
| 结构化日志 | `events.jsonl` + `meta.json`（`source: game_logic_sim`） |
| 唯一配表 | `Assets/StreamingAssets/Config/game_rules.yaml` |
| 质量配套 | `logic_qa/`（基线 + IF） |

对比跑：`scripts/diff_balance_reports.py`（同 seed 改配表前后各跑一批再 diff）。

## 3. 建议统计的指标

### 3.1 第一优先级（先做，就能调数值）

| 指标 | 定义（建议） | 用途 |
|--|--|--|
| **胜率** | 该角色为 `winner` 的对局占比 | 总强弱 |
| **死亡率** | 对局中出现 `death` 的占比（胜者可为 0） | 脆皮/坦度 |
| **平均存活回合** | 从开局到 `death` 的 `full_round`；存活到终局用终局回合 | 存活曲线 |
| **存活回合分布** | P25 / 中位 / P75 | 是否「早死一批、偶尔苟赢」 |
| **终局原因分布** | `last_standing` / `max_rounds` / 其它 | 局是否过长、平局过多 |
| **平均对局长度** | `full_rounds` 均值 | 节奏是否过拖 |

实现上：胜率可先读 `meta.json`；死亡/存活从 `death` + `clock`/`turn_start.round` 推；后续再写回 meta。

### 3.2 第二优先级（解释「为什么强/弱」）

| 指标 | 用途 |
|--|--|
| **伤害输出 / 承受**（总量、场均） | 输出型 vs 挨打型 |
| **伤害来源结构** | 近战 / 射击 / 炸弹 / 熔岩 / 燃烧 / 中毒… 谁在杀人 |
| **击杀数 / 被击杀数**（若日志可追溯 attacker） | 对位强度 |
| **濒死触发率** | `dying` 次数；猫等高机动是否常进濒死 |
| **技能使用率与收益** | 隐匿/抢夺/强化次数；用后 N 回合是否存活或击杀 |
| **关键道具持有率** | 玩偶、喷火、摩托、血瓶等「拿到过」占比 |
| **血瓶使用率与无效浪费** | 残血是否会奶；奶错时机 |
| **早期接触回合** | 首次对其他角色造成伤害的回合 | Rush vs 发育 |

### 3.3 第三优先级（深挖与对位）

| 指标 | 用途 |
|--|--|
| **角色对位胜率矩阵** | 在「最后两人」时 A vs B 谁更常赢（样本要够） |
| **熔岩期死亡率** | 缩圈后死亡占比 → 走位/移速数值 |
| **天气窗口表现** | 雨天防御下降期谁更吃亏 |
| **背包负荷/超重频率** | 负重规则是否拖累某角色 |
| **AI 策略分层** | 全 greedy / 全 random / 混合 分开报，避免混谈 |
| **种子稳定性** | 同配置多 seed 的胜率标准差 → 样本是否够 |

### 3.4 不建议第一期做的

- 实时在线看板、复杂 ETL  
- 用 Unity Editor 人手打几百局当主数据  
- 把平衡指标和 IF 异常检测揉成一个模型（目标不同，分开算）

## 4. 分阶段落地计划

### 阶段 A：最小可用（约 1～2 天）

1. 脚本：读一批 `output/match_*/`，聚合角色胜率、死亡率、平均/中位存活回合、终局原因。  
2. 输出 `reports/balance_report.json` + 控制台表。  
3. 约定默认实验：`--matches 200`（或 400），策略默认全 greedy；另存一份 random 对照。  
4. 文档写清：「指标 = 该 AI 下结果」。

验收：改猫 max_hp ±20% 重跑，胜率/存活应有可见变化。

### 阶段 B：解释层（约 2～3 天）

1. 从 `damage`/`death` 聚合输出、承伤、伤害来源。  
2. 必要时给 `damage` 补 `attacker` / `source`（小改引擎，非重写）。  
3. `meta.json` 增加 `per_role` 摘要，加速二次分析。

验收：能回答「某角色胜率低是因为早死于熔岩，还是输出不够」。

### 阶段 C：调参闭环（约 1～2 天）

1. `compare.py`：baseline 目录 vs candidate 目录，胜率/存活 diff + 简单显著性（如 Wilson 区间或 bootstrap）。  
2. 固定 seed 列表，保证对比公平。  
3. 可选：Streamlit 加「平衡」页（表 + 前后对比），不阻塞 CLI。

验收：一次「改 YAML → 跑批 → diff → 决定保留/回滚」闭环可复述。

### 阶段 D（可选，后期）

- 对位矩阵、熔岩/天气切片  
- 与 Unity 小样本人手局对照说明  
- CI 上只跑「烟雾级」50 局平衡摘要（完整 400 局留给本地/夜间）

## 5. 调数值工作流（推荐习惯）

1. **冻结 AI 与 seed 策略**（先全 greedy 定基线）。  
2. 跑 N 局 → 存 `reports/balance_baseline_xxx.json`。  
3. 只改一处数值（如猫 HP 或炸弹伤害）。  
4. 同 seed 再跑 N 局 → diff。  
5. 看胜率是否向 25% 附近靠拢，且死亡率/存活不过分极端。  
6. 用第二优先指标解释变化；手感再回 Unity 抽查。

经验阈值（可写进 `balance.yaml`，非硬性）：

- 四角色胜率长期落在约 **15%～35%** 可接受；长期 **&lt;10% 或 &gt;40%** 优先排查。  
- 某角色死亡率极高且平均存活显著偏低 → 优先坦度/机动/开局位置，而非只加攻击。  
- `max_rounds` 占比过高 → 先看节奏与缩圈，再看输出。

## 6. 风险与口径

1. **AI 偏差**：Greedy 爱炸/爱隐匿会抬高或压低某些角色；结论必须带策略标签。  
2. **仿真 ≠ Unity 100%**：规则主体对齐即可；以共用 YAML 为数值单一来源，减少双端漂移。  
3. **样本噪声**：&lt;100 局胜率抖动大；角色对比建议 ≥200，对位矩阵需要更多。  
4. **与异常检测区分**：胜率失衡 ≠ bug；基线报错才是逻辑缺陷。

## 8. 结论（直接回答）

- **仿真：用现有 `sim/`，不要重做。**  
- **要新建的是统计/对比层**（读日志 → 指标 → diff），引擎只需少量字段增强。  
- **第一期指标**：胜率、死亡率、存活时长（回合）、终局原因、对局长度。  
- **强烈建议接着做**：伤害结构、技能/关键道具、AI 策略分层、改参前后对比。  

确认要开工时，建议从阶段 A 的 `run_balance.py` + 三张核心表做起。

## 9. LLM 数值建议（`balance_advisor/`）

**先预处理，再调 API；不要把 `sim/output` 全量 events 喂给模型。**

| 步骤 | 内容 |
|--|--|
| 1 | `sim` 聚合 → `balance_report.json` |
| 2 | `balance_advisor` 组装：精简统计 + `game_rules.yaml` + 可选规则文档摘录 |
| 3 | 调兼容 OpenAI 的 Chat API → `advisor_suggestions.md` |

入口：`balance_advisor/scripts/run_advisor.py`（支持 `--dry-run` 只看预处理结果）。
