## 2. 四条标准（"能看懂"的定义）

| # | 标准 | 怎么检查 |
|---|---|---|
| 1 | **文件名即内容**：一个文件 = 一件事 | 打开目录，30 秒内能说出每个文件干什么；说不出的文件该拆或该删 |
| 2 | **一份数据一个地方** | 问"这个值改哪里"，只有一个答案；有第二个答案就是 bug |
| 3 | **改一处只影响一处** | 策划改数值不碰代码；程序改代码不动数值 |
| 4 | **一条命令能证明没改坏** | 见 §5。**不需要读懂代码就能判断对错** |

---

## 3. 三条预算规则（防止复杂性长回来）

1. **一份数据只许有一个权威。** 终态只有一处。
   **迁移期允许"影子副本"短暂并存**，但必须同时满足三条，缺一条就是永久双源：
   ① 副本由脚本生成，不手抄；② 每次改动都跑一致性校验，漂移即报错；③ 事先写明退场条件与期限。
2. **一个开关只许出现在一个装配点。** 散落超过一处的开关，一律视为 bug 温床。
3. **引入新概念（表 / 模式 / 新目录）之前，先说明它替换掉了哪条旧路径。** 替换不了就别加——否则只是多造一条路。

---

## 4. 两种复杂度，别混为一谈

| 类型 | 例子 | 怎么办 |
|---|---|---|
| **本质复杂度**（删不掉） | 六种攻击方式、天气×地形×状态三层叠加、四种模式共用一套规则 | **隔离**：关进少数几个文件，不让它扩散 |
| **偶然复杂度**（能删） | 名单存两份、状态四条倒数路径、元数据在 C# 又在表里、16 处 `if (IsLogicSim)`、六份投掷模板复制 | **删除**：合并成一条路 |

**判据**：如果一个"复杂"是规则本身要求的，那是本质的；如果是"同一件事的第二份实现"，那是偶然的，删。

## 5. 验收线：同种子对拍

**任何改动，都必须能在不读代码的前提下被判断"改坏了没有"。**

```bash
cd Tools/sim
python scripts/run_batch.py --matches 100 --seed 50000 --collect balance --out output/det_<本次名字>
```

判定标准：与基线 `Tools/sim/output/det_a` **逐局比对** `winner / reason / full_rounds / per_role`，
**必须 0 差异**。

- 0 差异 → 通过。改动属于"结构不变、行为不变"
- 有差异 → 停手，定位到第一个分叉的种子，不猜
- 改的本来就是行为（如调数值）→ 另开一批对比，并写进变更记录

**基线可信的前提已经验证过**：同种子连跑两批（`det_a` / `det_b`）100 局全一致，引擎是确定性的。

## 7. 这份文档怎么用

**动手前**：这次改动，删掉哪条路？（答不上来，说明这是加法，不是减法）

**提交前**：四条标准有没有被破坏？

**提交后**：对拍是 0 差异吗？是 → 合并；否 → 回滚。

**每完成一条欠账**：回来把 §6 那一行改成 ✅，写上提交号。**这张表就是项目的体检单。**
